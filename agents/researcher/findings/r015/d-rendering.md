## The best few, in more depth

### 1. Cycles' own reuse switches: Light Groups, Persistent Data, a fixed Seed (Blender 4.5 manual)

**The work it avoids redoing.** Light Groups: re-rendering when only the colour or strength of lights changes. Each group renders as its own pass, and "by making more complex combinations, it's possible to change the color and intensity of individual lights without having to re-render" (manual, View Layer → Passes → Light Groups). The World background can be put in a group. Persistent Data: rebuilding render data for each frame or re-render; the option will "Keep render data in memory after rendering for faster re-renders and animation renders at the cost of extra memory usage" (manual, Performance → Final Render). A fixed Seed: not reuse of computation but of random numbers. With "Use Animated Seed" off, consecutive renders share a noise pattern, which is the correlated sampling that Residual path integrals (entry 6) uses as its baseline.

**Numbers.** None; the manual reports no timings. The test bed would have to measure them, which is the point of METHOD.md step 4.

**Conditions stated.** Light Groups are Cycles only. Persistent Data with several view layers keeps only one layer's data, plus objects shared between layers, and costs memory. Path guiding, a related switch, is CPU only.

**Failure modes.** Persistent Data has a run of bug reports where stale data changes the image: animated curves flickering with motion blur (T99281), armatures snapping to the last rendered pose (#125594), animated data ignored (#87723), video textures not updating (#92980), GPU memory filling on macOS (#110520). These were seen as titles and snippets, across Blender versions, so whether any still applies to 4.5 is unknown. For Light Groups, three limits follow from linearity and are reasoned, not stated: recombination is exact for scaling the strength or colour of a group, not for moving or resizing a light or rotating an HDRI; it does not cover a change to the garment's own colour, because rendering is not linear in albedo once light bounces more than once; and denoising each pass and then summing is not the same as denoising the sum, because the denoiser is not linear.

**What it would take under the constraints.** Nothing new to install; all three work on the Mac's CPU and Metal. Two uses follow (both reasoned, untested). For the light estimate: split candidate lighting into a few groups (World HDRI, key, fill, rim), render each pass once, and fit the group weights to the photo by least squares in numpy, so the fitting loop never re-renders. For many frames of one garment: turn Persistent Data on; the garment's own mesh still changes each frame and must be rebuilt, so the saving is in the body, backdrop and textures, and has to be measured. For comparing looks: keep the seed fixed so that ΔE between two looks measures the change and not the noise.

**Test-bed problem addressed.** Many near-identical looks and frames; the light estimate (fitting light weights without re-rendering).

### 2. DiffusionLight-Turbo (Chinchuthakun et al., arXiv 2507.01305, v2 January 2026)

**The work it avoids redoing.** DiffusionLight inpaints many chrome balls from different noise seeds and takes a median, because single samples are unreliable. Turbo trains a LoRA to predict that averaged ball directly, then runs one denoising pass that starts with the Turbo LoRA and switches to the exposure LoRA at 0.8T ("Turbo-Swapping", Sec. VI). The many-sample median is paid for once, in training, and reused for every image: across many instances, and the answer changes slightly.

**Numbers (Table I, "measured on a single RTX 3090 Ti GPU over 10 random samples").** Time per estimate: DiffusionLight 31.889 min, Turbo 0.535 min. Mirror-ball scores, DiffusionLight vs Turbo: Laval Indoor si-RMSE 0.597 vs 0.620, angular error 5.936 vs 6.114; Poly Haven si-RMSE 0.664 vs 0.680, angular error 4.286 vs 4.504. On Laval Indoor's diffuse ball Turbo is slightly better on si-RMSE (0.130 vs 0.140). Table VI: cutting iterations from two to one roughly halves runtime "with minimal quality degradation". Evaluation panoramas are 128 × 256.

**Conditions stated.** One LDR image; an orthographic projection is assumed when converting the ball to an environment map, since focal length is unknown; ball placement relies on an off-the-shelf depth predictor.

**Failure modes stated (Sec. VIII, Figs. 11–12).** Overhead and bird's-eye views; "macro and close-up images may lack sufficient shading cues"; "images with empty or solid backgrounds often cause our method to hallucinate some details onto the balls, and the balls may appear too dark, especially on a white background", listed as "high-key or low-key images with solid backgrounds"; styles far from natural photos; hallucinated outdoor scenes on indoor inputs "when visual cues are limited", which is "more pronounced in DiffusionLight-Turbo"; wrong depth on reflective, textureless or overexposed surfaces.

**What it would take under the constraints.** Code and LoRA are MIT. The pipeline is SDXL plus a depth ControlNet through diffusers. Diffusers runs on MPS, but SDXL with a ControlNet in 16 GB of unified memory is tight, and expect minutes rather than 30 s per estimate (reasoned, untested). The official Turbo repository is small (2 stars, last push July 2025).

**Test-bed problem addressed.** The light estimate on a dark, decorated backdrop. Turbo does not fix it: the paper's own failure list (low-key image, few shading cues, outdoor hallucination when cues are limited) describes that photo, so the failure is a stated limitation of the method rather than a fault in the test bed's setup. The match is partial, because the backdrop is decorated rather than solid. What Turbo changes is the cost of each attempt, which makes trying several crops or exposure-adjusted inputs affordable. A light probe that does not depend on the backdrop (SPLiT's face, or the garment itself in entry 1's least-squares fit) is the more direct fix and is untested.

### 3. Woven Fabric Capture with a Reflection-Transmission Photo Pair (Tang, Li, Hašan, Yang, Wang, SIGGRAPH 2024)

**The work it avoids redoing.** Not a reuse technique. One small part is: a network trained on rendered images gives the starting guess that differentiable optimisation then refines.

**Numbers.** Network training "four hours on a single A40 GPU". Optimisation: Adam, learning rate 0.01, 300 iterations, "about four minutes on an NVIDIA 4060 GPU". Input: 4K raw phone images cropped and downsampled to 512 × 512. Training data: 1,280 rendered images per weave pattern, for five patterns (twill, satin, plain, and twill and satin rotated 90 degrees). The main text gives no quantitative parameter error; it says predicted roughness and thickness differ from ground truth by an acceptable amount, with values in a supplementary table I did not read.

**Conditions stated.** A flat swatch in a holder; one phone camera; two point lights, one in front and one behind; calibrated light brightness and vignetting. The BSDF has two SpongeCake-style layers (top and bottom yarn), SGGX single scattering, a new ASGGX lobe for multiple scattering, a diffuse term, a tension-aware thickness function, and a gap scaling factor for the openings between yarns. Out-of-focus light seen through the gaps is matched with a Gaussian around the projected light. Only the trained weave patterns are supported; others need retraining. The renderer is the authors' own differentiable PyTorch code, not Mitsuba.

**The statement that matters most for the test bed.** "Fabrics with different thicknesses might have similar reflection images, but very different backlighting (light transmission) behavior. … This effect can no longer be estimated from a single image; both the reflection and transmission images are needed to recover the complete set of fabric parameters" (Sec. 1).

**Failure modes and limits stated.** No variation in yarn diameter, no yarn sliding, no wrinkles or flyaway fibres, which causes mismatches; colour bias and highlight mismatch in the network's prediction before optimisation; more parameters would make optimisation with two images harder; knitted fabric left to future work. Sheer, thin and printed fabrics are not discussed.

**What it would take under the constraints.** GPL-3.0 code, plain PyTorch, which falls back to CPU by itself (`utils.py`), so it runs; MPS would need an edit; CPU optimisation time is unmeasured (four minutes on a 4060 suggests tens of minutes, reasoned). It needs a physical swatch and a back-lit photo, which a reference photo does not give. Its BSDF is not a Cycles node; a rough Cycles stand-in would map gap scaling to coverage (a Transparent BSDF mix, or alpha), diffuse transmission to the Translucent BSDF, and the specular lobe to Sheen or Principled (reasoned).

**Test-bed problem addressed.** The sheer dupatta's density, set by eye. Without a swatch, what transfers is the argument: a reflection-only view cannot pin down how much light passes through. In a reference photo the parts of the dupatta that lie over the kameez or skin act as a crude transmission view, a known background seen through the cloth (reasoned, untested). That suggests fitting the dupatta's coverage only in those overlap regions.

### 4. Colorful Diffuse Intrinsic Image Decomposition in the Wild (Careaga, Aksoy, ACM TOG 2024), with Marigold-IID as the open alternative

**The work it avoids redoing.** Not a reuse technique beyond a learned model reused for every image.

**Numbers.** "Our full pipeline takes around a second on average to generate a high-resolution result", against "> 10 seconds" for methods that refine or average (Sec. 4; the hardware for that timing is not given in the passage I read). Four networks, 337 million parameters in total; a single-network baseline needed a 40 GB GPU to train at batch size 2.

**Conditions stated.** It starts from the grayscale ordinal-shading estimate (their 2023 method, which the test bed knows), then estimates low-resolution shading colour, then high-resolution albedo, then removes the Lambertian assumption by splitting out a specular residual. The final diffuse network is trained only on a synthetic indoor dataset; the authors show it generalising to faces and outdoor scenes.

**Failure modes stated.** "While our networks are trained to account for erroneous initial estimations, they may also propagate some of the challenging mistakes" (Sec. 6, Fig. 12: hard balcony shadows left in the albedo), which can be fixed by editing the input. In their comparisons, RGB↔X "may cause cartoonization of human faces".

**What it would take under the constraints.** Same package as the 2023 method (`load_models('v2')` in compphoto/Intrinsic), under the same "academic use only" licence with a patent notice: free, not open source. Whether v2 runs on the test bed's Mac setup was not checked. Marigold-IID-Lighting (Ke et al. 2025) gives the same three outputs (albedo, diffuse shading, non-diffuse residual) with Apache-2.0 code and openrail++ weights; it is a Stable Diffusion fine-tune, so expect it to be slow on CPU, and MPS through diffusers is untested.

**Test-bed problem addressed.** Prints projected from the photo carry the photo's shading. Projecting the diffuse albedo instead of the raw photo would let Cycles supply the shading, and the specular residual would keep metallic or glossy highlights out of the print texture (reasoned). Whether that lowers the render-to-photo ΔE is the test; the decomposition could also add its own errors to the print colour, which the same ΔE would show.

### 5. Parameter-space ReSTIR for Differentiable and Inverse Rendering (Chang, Sivaram, Nowrouzezahrai, Hachisuka, Ramamoorthi, Li, SIGGRAPH 2023)

**The work it avoids redoing.** In inverse rendering each gradient-descent iteration draws fresh Monte Carlo samples and discards them, though the scene barely changes between iterations. The paper keeps reservoirs of derivative samples per texel and resamples across iterations (ReSTIR's temporal reuse, adapted). Across runs; cost only by design ("we reuse samples to reduce variance at each iteration without bias, effectively increasing sample count", Sec. 5).

**Numbers.** Implemented in Mitsuba 3's GPU backend; "All experiments ran on an NVIDIA GeForce RTX 2080 Ti". Timings exclude Dr.Jit's tracing and compilation overhead: "we excluded this overhead, and report the time spent exclusively on executing the GPU rendering kernels". Each experiment optimises one 2048 × 2048 texture of Disney principled BSDF parameters from a single view, with 32 spp for the forward pass and 1 spp for the derivative pass. On the Christmas-tree scene their derivatives have "over four times lower error than Mitsuba 3's estimates" at equal time. Across Adam settings (β1 in [0.8, 0.95], β2 in [0.99, 0.9999]) the improvement held, "with less than a 10% difference in the reconstruction errors".

**Conditions stated.** Direct lighting only; texture optimisation; consecutive gradients must be "sufficiently correlated".

**Failure modes and limits stated.** High learning rates change parameters by large margins and break the correlation, though the method still helped empirically; "the relationship between gradient estimation errors and convergence speed of optimization steps remains generally unclear". Because the JIT overhead was excluded, wall-clock gains would be smaller than the reported kernel-time gains (reasoned from their statement).

**What it would take under the constraints.** It does not run: the code supports only `cuda_ad_rgb` and needs a Turing-or-newer NVIDIA GPU, and the reservoir operation is written for Dr.Jit's CUDA backend (README). Porting it to Mitsuba's LLVM (CPU) backend would mean rewriting that operation; substantial. The cheap partial reuse the test bed already gets is Adam's moving averages, which the paper says their method beats.

**Test-bed problem addressed.** If the test bed fits fabric or light parameters with Mitsuba 3 on CPU, every iteration re-renders a near-identical scene; this is the published reuse for that loop, and it says when it stops paying (large steps). Balint et al. 2023 is the sibling method, abstract only.

### 6. Residual path integrals for re-rendering (Xu, Li, Georgiev, Hedstrom, Ramamoorthi, CGF 43(4), EGSR 2024)

**The work it avoids redoing.** Rendering a whole new frame when only a small object moved or one material changed. It renders only the difference between the two scenes as its own light-transport integral, sampling paths that start from the changed objects. Across runs; cost only (they verified the images converge to the reference).

**Numbers.** Standalone C++ renderer on Intel Embree, "run on an AMD Ryzen 16-Core Processor". "Overall, we achieve speedups ranging from 2x to 5x (and 4x to 16x for material editing) compared to Correlated PT, and frequently observe orders of magnitude speedups compared to traditional path tracing" (Sec. 6.2, equal-time MSE). Correlated PT is the baseline that renders both scenes with the same random numbers.

**Conditions stated.** Only a small part of the scene changes. Material editing is "a simpler problem" that needs half of the method. When the camera or lights move, the best strategy "degenerates into camera/light tracing".

**Failure modes stated.** Residual images have negative values, so at low sample counts the final image shows dark pixels that "disappear with sufficient samples"; their sampling starts mid-scene and suffers more cache misses; plain path tracing does better when the scene favours tracing from the camera.

**What it would take under the constraints.** CPU-only, so the Mac is fine in principle, but I found no code link, and it is a separate renderer, not Cycles. What the test bed can take today is the baseline: render each look with the same Cycles seed so the noise is shared and the difference between looks is cleaner (reasoned; how much cleaner in Cycles is untested).

**Test-bed problem addressed.** Many near-identical looks of one garment (colour or material variants): the published evidence that rendering the difference is cheaper than rendering each look, and by how much on a CPU.

## What the area doesn't offer

Nothing found fits a sheer fabric's optics to an ordinary reference photo: every recent fabric-capture method needs a controlled capture of a swatch (front- and back-lit photos, a close-up, or a microscope image), and Tang et al. argue that a reflection-only view cannot recover transmission at all, so the test bed's by-eye density has no published replacement, only the argument for fitting it where a known background shows through. The recent fabric BSDFs (Zhu et al. 2023, Soh and Montazeri 2024, Tang et al. 2024) live in research renderers, not Cycles, and the neural one cannot do printed cloth. Lighting estimation from one photo of a person is thin: the strong general method (DiffusionLight and Turbo) names low-key, low-cue images as a failure case, the human-specific methods mostly relight without returning an environment map, and the one face-based estimator with code (SPLiT) is trained on synthetic faces and untested here. Gaussian splatting and other neural rendering offer nothing for a single photo except generative avatars that hallucinate the back and carry no sewing pattern or fabric optics; Metal trainers exist (msplat, OpenSplat, Brush) but only matter with many views. Back-of-garment texture completion has papers (DeepIron, SiTH, Garment3DGen, GarmentPainter) but either no code or CUDA-only code that textures a body mesh, not pattern pieces. Reuse inside rendering is mature for real-time GPUs (ReSTIR and its descendants, DXR or CUDA only) and for inverse rendering on NVIDIA hardware (Parameter-space ReSTIR), while the CPU-friendly reuse for near-identical scenes (Residual path integrals) has no code; what is actually usable on the Mac is Cycles' own switches (Light Groups, Persistent Data, a fixed seed, CPU path guiding), which come with no published measurements, so their value is a test-bed measurement waiting to be made. Finally, glTF cannot carry the dupatta's optics as built in Cycles: the Blender 4.5 exporter writes KHR_materials_sheen, KHR_materials_transmission and KHR_materials_volume, but nothing for diffuse transmission (Cycles' Translucent BSDF), and KHR_materials_diffuse_transmission is still a "Release Candidate" at Khronos; meanwhile the manual says glTF's alpha blending "is intended to represent physical materials that are partially missing from the specified geometry, such as medical gauze wrap", which suggests the sheer dupatta's see-through coverage belongs in base-colour alpha rather than in transmission when exported (reasoned from the manual's wording, untested in any viewer).
